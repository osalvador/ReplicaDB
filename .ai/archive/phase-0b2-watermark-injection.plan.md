# Implementation Plan: Phase 0-b2 — Watermark Injection

## Task Source

`ARCHITECTURE_DECISIONS.md`, Decision 3 ("Incremental watermarks") and the "Phase 0: Core and State Foundation" → "Core changes" item 1 ("Watermark injection"). No JIRA ticket.

This is the follow-up plan explicitly reserved by `.ai/archive/phase-0b1-cancellation-plumbing.plan.md`, which split "Phase 0-b" into cancellation (delivered, commit `4dd4cb5`) and watermark injection (this plan), since combining both would have exceeded ~35-45 tasks.

Acceptance criteria extracted from Decision 3 and the Phase 0 exit criteria, scoped to this plan:

- A run can declare **one source column** as the watermark column, and an optional last-committed value, through CLI/options-file configuration (no `JobDefinition`/database layer exists yet — that is Phase 0-c).
- The predicate is injected by the engine as `AND <watermarkColumn> > ?`, bound as a typed parameter inferred from the source column's JDBC metadata — **never concatenated into SQL**.
- Absent a last-committed value, the run replicates everything the query returns (first-run behavior).
- Each parallel `ReplicaTask` reports its highest observed value in `ReplicaTaskResult.watermarkCandidate`; the executor reduces all tasks' candidates to one value for the run.
- The reduced candidate is exposed only **after `postSinkTasks()` (staging load + merge) succeeds** — a failed or cancelled run leaves it unset/unchanged.
- CLI behavior, exit codes, and existing `ToolOptions` configuration remain compatible.

**Explicitly out of scope for this plan**:
- `JobDefinition`/`JobRun` persistence, Flyway/PostgreSQL, the claim mechanism, and the `replicadb`/`replicadb-server` artifact split (deferred to Phase 0-c per the architecture document). This plan cannot "commit" a watermark to a database — it exposes the reduced candidate on `ReplicationExecutionContext` for a future Phase 0-c caller to read and persist.
- Non-SQL managers: `MongoDBManager`, `KafkaManager`, `S3Manager`, `LocalFileManager`/`OrcFileManager`/CSV file managers. None of them build a bindable SQL `WHERE` clause the way the 8 JDBC managers do, and Mongo/Kafka/S3/file already have documented merge/incremental limitations from prior phases. Watermark injection here is limited to `Db2Manager`, `DenodoManager` (source-only — Denodo cannot be a sink), `MySQLManager`, `OracleManager`, `PostgresqlManager`, `SqliteManager`, `SQLServerManager`, `StandardJDBCManager`.
- Multi-column or expression watermarks, and watermark support combined with `replication.table.*` multi-table entries (each entry would need its own value — out of scope, consistent with Decision 1's "N tables means N job definitions").
- Read-lag configuration for late-committing source transactions (Decision 3 documents this as a future, separately-tunable knob).
- An actual HTTP/API surface to trigger runs or read the committed watermark — Phase 1 introduces the API. This plan only builds the internal mechanism a future job-execution service will call.

## Overview

ReplicaDB's `incremental` mode today relies entirely on the user manually supplying `--source-where` and a merge-capable sink; there is no automated "read only what changed since last time" mechanism, and `ReplicaTaskResult.watermarkCandidate` (added as reserved plumbing in Phase 0-a) is always `null`. This plan lets a run declare a watermark column and a last-committed value, injects a bound `> ?` predicate into the 8 JDBC-based managers' existing query-building code, infers the bind type from source column metadata (reusing the existing `probeSourceMetadata()`/`ColumnDescriptor` machinery built for auto-create), computes each task's highest observed value via a lightweight follow-up `MAX()` probe on the same connection, and reduces all tasks' candidates into one run-level value exposed on `ReplicationExecutionContext` only after the merge succeeds.

## Architecture & Design

**Approach**: Read-side MAX probe. Each manager's `readTable()` already builds a dialect-specific SQL string and calls the shared `SqlManager.execute(String stmt, Object... args)` with positional bind values (this is the same choke point Phase 0-b1 used to centralize source-side statement tracking). This plan:

1. Adds two new `ToolOptions` fields — `incrementalWatermarkColumn` and `incrementalWatermarkValue` — parsed from `--incremental-watermark-column`/`--incremental-watermark-value` (and their options-file equivalents), validated against `mode`/`replication.table.*`.
2. Adds a `manager.util.WatermarkBinder` helper that (a) resolves the watermark column's JDBC type from `options.getSourceColumnDescriptors()` (already populated by `probeSourceMetadata()`), (b) converts the raw CLI string into a typed bind object (`BigDecimal`, `Timestamp`, `Date`, or `String`) for `PreparedStatement.setObject()`, and (c) compares two driver-formatted candidate strings type-aware for run-level reduction.
3. Widens the `preSourceTasks()` metadata-probe gate (currently `sinkAutoCreate`-only) to also run when a watermark column is declared, so type inference works even without auto-create.
4. Centralizes "the last SQL text and bind args a source manager executed" as two new protected fields on `SqlManager`, set inside the existing `execute(...)` method (one file change covers all 8 managers), and adds a concrete `resolveWatermarkCandidate(int taskId)` method on `SqlManager` that re-uses those fields to run `SELECT MAX(<col>) FROM (<lastReadSql>) wm_probe` with the same bind args. `ConnManager` gets a default no-op (`null`) implementation so non-SQL managers need no changes.
5. Each of the 8 JDBC managers gets a small, mechanical change to its own `readTable()`: append `AND <escapeColName(watermarkColumn)> > ?` to its already-built WHERE clause (or add `WHERE` if none exists) and add the converted bind value to its call to `execute(...)`, **at the correct position relative to any existing bind args** (partition offsets, chunk sizes, etc.), since JDBC binds are positional.
6. `ReplicaTask.call()` calls `sourceDs.resolveWatermarkCandidate(taskId)` after a successful `insertDataToTable(...)` and puts the result into `ReplicaTaskResult.watermarkCandidate`.
7. `ReplicaDB.summarize(...)` is widened with an overload that reduces all non-null candidates to the maximum using `WatermarkBinder`'s type-aware comparator; `executeSingleReplication(...)` calls it and, **only if `executePostTasks()` (which runs `mergeStagingTable()`/`atomicInsertStagingTable()`) completes without throwing**, stores the reduced value on `ReplicationExecutionContext` via a new `setWatermarkCandidate(String)`/`getWatermarkCandidate()` pair — the same "attach state to the existing per-run context" pattern Phase 0-a/0-b1 used. A future Phase 0-c job-execution service reads it from there; this plan does not persist it anywhere.

**Rejected alternative**: Streaming-captured value via a `ResultSet` proxy (tracking the watermark column's value as rows pass through to the sink, instead of a follow-up query). Rejected because it requires wrapping every `ResultSet` `ReplicaTask` hands to a sink (JDBC-backed, custom row-sets, and Mongo/CSV/ORC alike) behind a generic, type-erased interception layer, is harder to unit test deterministically, and buys only the avoidance of one cheap, single-row aggregate query per task.

**Rejected alternative**: Reducing manager scope to 4 core managers now (StandardJDBC/PostgreSQL/MySQL/Oracle) and deferring Db2/SQLServer/SQLite/Denodo. Rejected because it would re-split an already-deferred item a second time and leave the "all managers wired consistently" precedent from Phase 0-b1 broken; the per-manager diffs are small enough (2-4 lines) that grouping them into 4 tasks keeps this plan under the ~20-task guard without reducing scope.
