# Implementation Plan: Migrate Test Infrastructure to JUnit 6

## Task Source — GitHub PR #242 — `chore(deps-dev): bump org.junit.jupiter:junit-jupiter-api from 5.4.2 to 6.0.3`

Acceptance criteria:

- Upgrade the JUnit Jupiter API to 6.0.3 as proposed by PR #242.
- Keep the Jupiter API, parameters module, and engine on one compatible 6.0.3 version.
- Run the Maven test lifecycle with a JUnit 6-compatible Surefire version.
- Use Java 17 wherever Maven, CI, or the packaged runtime executes ReplicaDB, because JUnit 6 requires Java 17 or newer.
- Preserve the existing Testcontainers lifecycle and test behavior across unit, non-integration, and database integration suites.
- Make the repository's runtime images and written Java-version requirements agree with the new baseline.
- Produce a clean build and passing CI checks for the PR branch.

## Overview

PR #242 changes only `junit-jupiter-api`, while `junit-jupiter-params` and `junit-jupiter-engine` remain on 5.4.2. The repository also targets Java 11 and pins Maven Surefire to 2.22.1, both of which are incompatible with JUnit 6. The failed PR checks across all integration matrices and the non-integration job are therefore expected from an incomplete dependency migration rather than from one database adapter.

This plan applies the complete migration selected during exploration: align the JUnit modules at 6.0.3, establish Java 17 as the build and runtime baseline, use a JUnit 6-compatible Surefire release, remove unused JUnit 4 `@Rule` residue from tests, and update CI, container images, and repository guidance. No production replication algorithm or database-manager behavior should change.

## Approach Selection

### Considered: Minimal CI unblock

Update the JUnit modules, Java toolchain, and Surefire only. This is the smallest patch, but it leaves Java 11 container images and documentation behind and preserves obsolete JUnit 4 imports that can disappear from transitive dependencies later.

### Selected: Complete compatibility migration

Update the build, test sources, CI workflows, runtime images, and Java-version guidance together. This keeps the declared Java contract coherent and makes the JUnit 4 cleanup explicit while retaining the existing Testcontainers implementation. It is the recommended approach because the project distributes executable Docker images and documents Java 11 as a supported runtime.

Estimated size: 9 focused tasks across build configuration, tests, automation, packaging, documentation, and verification.

### Considered: Defer JUnit 6

Keep JUnit 5 and potentially upgrade to a later JUnit 5 release. This preserves Java 11 compatibility but does not approve or resolve PR #242, so it is out of scope for this plan.

## Architecture & Design

**Approach:** Complete compatibility migration.

- **Build boundary:** Keep all JUnit and Surefire changes in `pom.xml`; do not add JUnit dependencies to production scope.
- **JUnit versions:** Define one `6.0.3` property and use it for `junit-jupiter-api`, `junit-jupiter-params`, and `junit-jupiter-engine`. Keep the Testcontainers `org.testcontainers:junit-jupiter` module at the existing Testcontainers version; it is a different artifact and must not be confused with the JUnit Jupiter engine.
- **Maven execution:** Target Java 17 and explicitly resolve Maven Surefire to a 3.x release compatible with JUnit Platform 6. The current `pluginManagement` entry alone must not be assumed to control the default test lifecycle; verify the effective POM and add an explicit build plugin entry if required.
- **Test lifecycle:** Existing tests use Jupiter annotations and Testcontainers' Jupiter extension. The `org.junit.Rule` imports and `@Rule` annotations are unused JUnit 4 residue around manually-started singleton containers. Remove only those imports and annotations; preserve existing `@Testcontainers`, `@Container`, setup, teardown, and `getInstance()` calls.
- **Execution environments:** Set JDK 17 in all workflows and move both runtime images to Java 17 images. This intentionally changes ReplicaDB's minimum runtime from Java 11 to Java 17.
- **Performance and security:** No replication-path performance or credential-handling behavior changes are planned. Java 17 and new base images may change default TLS/provider behavior, so the package and container smoke checks must verify startup and the existing CI test matrix.
- **Known local prerequisite:** The current shell has no selected Java runtime, so local Maven verification requires selecting an installed JDK 17 before implementation begins. Docker must be available for Testcontainers and image checks.
