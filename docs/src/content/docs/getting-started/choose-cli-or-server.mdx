---
title: Choose CLI or Server
description: Compare how the standalone CLI and managed Server run, schedule, and track replications.
---

CLI and Server use the same replication engine. Choose based on who will own
the execution, its configuration, and its history.

| What you need | Standalone CLI | Managed Server |
| --- | --- | --- |
| Start a run | Invoke the launcher with arguments or an options file. | Trigger a saved job from the web interface or API. |
| Run on a schedule | Use an external scheduler or pipeline. | Set a schedule on a managed job. |
| Store configuration | Keep options and connection settings in your automation. | Save reusable datasource profiles and job definitions in Server. |
| Control access | Manage process, file, and database access in your environment. | Use the Server sign-in, roles, and resource permissions alongside database access. |
| Inspect results | Collect process logs and exit codes. | Inspect persisted run status, diagnostics, and retry history. |

## Choose your quickstart

Use the [CLI quickstart](/ReplicaDB/getting-started/cli-quickstart/) for a
one-off migration, a shell script, or a pipeline that already manages
scheduling and logging. The CLI runs as a standalone Java process.

Use the [Server quickstart](/ReplicaDB/getting-started/server-quickstart/)
for a team that needs reusable jobs, shared visibility, or schedules.
Local mode runs the Server and its embedded metadata PostgreSQL on one host.
An [API and worker deployment](/ReplicaDB/operations/distributed-deployment/)
uses an external metadata PostgreSQL database.

Both quickstarts copy the same order from `shop.orders` to
`reporting.orders`. In both paths, the
[connector pair](/ReplicaDB/connectors/) and
[replication mode](/ReplicaDB/cli/replication-modes/) determine how the
destination is written.
