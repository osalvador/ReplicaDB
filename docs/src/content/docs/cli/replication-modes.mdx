## Choose a mode

The mode controls how ReplicaDB writes the selected rows. Use `mode` in
a CLI options file, `--mode` on the command line, or **Mode** in a Server job.
Check the [connector matrix](/ReplicaDB/connectors/) for support at both ends.
The flows and example below use [PostgreSQL](/ReplicaDB/connectors/postgresql/)
as both source and sink.

| Choose | When | What readers may see |
| --- | --- | --- |
| `complete` (default) | You can clear and reload the destination. | The destination can be empty or partially repopulated during a run or after an interruption. |
| `complete-atomic` | You need to publish a full replacement in one transaction. | A new ordinary PostgreSQL read sees the previous committed rows until the replacement commits. |
| `incremental` | You can select new and changed rows and have a destination primary key. | The merge updates matching keys and inserts new keys. Rows absent from the selection stay in the destination. |

## Prepare the comparison

Use [Sample data](/ReplicaDB/getting-started/sample-data/) to create the lab.
The [CLI quickstart](/ReplicaDB/getting-started/cli-quickstart/) supplies the
`orders.conf` used below. The [Server quickstart](/ReplicaDB/getting-started/server-quickstart/)
supplies the datasource profiles and the job settings. Run the commands only
against the disposable tables from this walkthrough.

Update the source once to simulate the next batch of orders:

```bash
docker exec -i replicadb-docs-demo psql -v ON_ERROR_STOP=1 -U demo -d replicadb_demo <<'SQL'
UPDATE shop.orders SET status = 'paid', change_seq = 11 WHERE id = 1;
INSERT INTO shop.orders VALUES (2, 'pending', 12);
SQL
```

Before each mode, reset the destination to the earlier copy of order `1`
plus order `9`, which exists only in reporting:

```bash
docker exec -i replicadb-docs-demo psql -v ON_ERROR_STOP=1 -U demo -d replicadb_demo <<'SQL'
TRUNCATE reporting.orders;
INSERT INTO reporting.orders VALUES (1, 'pending', 10), (9, 'archived', 8);
SQL
```

Verify the results after each run:

```bash
docker exec replicadb-docs-demo psql -U demo -d replicadb_demo \
  -c 'SELECT id, status, change_seq FROM reporting.orders ORDER BY id;'
```

## Complete

1. ReplicaDB prepares the destination, clearing the sink by default in this lab.
2. The task reads both source rows and copies them directly to the destination.
3. Orders `1` and `2` are now in reporting. The older order `9` was cleared.

An interruption after preparation can leave the destination empty or partially
repopulated. A retry starts the complete flow again.

```bash
./bin/replicadb --options-file ./orders.conf --mode complete
```

In Server, set **Mode** to **Complete mode** and leave **Truncate sink table**
enabled. Run the job manually and wait for `SUCCEEDED`.

| id | status | change_seq |
| --- | --- | --- |
| 1 | paid | 11 |
| 2 | pending | 12 |

## Complete-atomic

1. ReplicaDB creates a staging table and copies both source rows into it.
2. The PostgreSQL path can start deleting the old destination rows while
   staging loads. That deletion is part of an uncommitted transaction.
3. ReplicaDB inserts the staged rows into the destination and commits the
   insertion and deletion together in the atomic replacement transaction.

An ordinary read in a separate PostgreSQL session using the default isolation
level sees the old committed rows before the commit and the new rows after it.
A failure before the commit leaves the old rows visible. An interruption
around commit warrants checking the destination before retrying.

ReplicaDB attempts to drop an automatically created staging table during
cleanup. A sudden process exit can interrupt cleanup. A staging table supplied
by the user is retained. Check sink permissions and storage for staging
before choosing this mode.

```bash
./bin/replicadb --options-file ./orders.conf --mode complete-atomic
```

In Server, set **Mode** to **Complete atomic mode**, leave staging fields empty
to use the connector's generated table, and run the job manually.

| id | status | change_seq |
| --- | --- | --- |
| 1 | paid | 11 |
| 2 | pending | 12 |

## Incremental

1. Use the earlier value `10` as the [watermark](/ReplicaDB/cli/incremental-watermarks/).
   ReplicaDB adds a source predicate equivalent to `change_seq > 10`, which
   selects orders `1` and `2`.
2. ReplicaDB copies the selected rows into staging. PostgreSQL uses the
   destination primary key `id` to merge matched keys and insert new keys.
3. The merge changes order `1` to `paid` and inserts order `2`. It does not
   infer deleted source rows, so order `9` remains.
4. The engine computes `12` as the candidate for the next run. Server
   persists it after successful finalization. The standalone CLI caller
   supplies the lower bound again for each invocation.

```bash
./bin/replicadb --options-file ./orders.conf --mode incremental \
  --sink-staging-schema public \
  --incremental-watermark-column change_seq --incremental-watermark-value 10
```

In Server, create a new job using the same two tables and select
**Incremental mode**. In **Sink**, set **Staging schema** to `public`. Set
**Incremental watermark column** to `change_seq` and **Initial watermark
value** to `10`. Run it manually.

This lab uses `public` for staging because the PostgreSQL incremental merge
in ReplicaDB 1.0.3 resolves the staging table through the connection's search
path. The final table is still `reporting.orders`.

| id | status | change_seq |
| --- | --- | --- |
| 1 | paid | 11 |
| 2 | pending | 12 |
| 9 | archived | 8 |

Try another run with the same source data. In CLI, pass `12` explicitly for
this exercise. In Server, run the same incremental job again. Neither run
should change the destination. A managed failure or cancellation keeps the
previous committed watermark even if some destination writes took effect.

## Verify and retry

Inspect the destination before retrying a failed or cancelled run. A retry
starts the transfer from the beginning of its selected input. The CLI reports
error as exit code `1` and cancellation as `2`. For a managed run, use the
[run details](/ReplicaDB/server/runs-and-diagnostics/) and
[recovery guide](/ReplicaDB/operations/failure-recovery/).
